## Session — recovery lifecycle, mandatory write freeze, branch minimality (v5.13.2)

Third external review round on `bugs/2026/08/plastic-bag-count`. The round-two findings were
re-checked against the working tree rather than `HEAD`: survivor preflight, `rank:objects`
reconciliation and the pivot write lock were already in place, so only the two genuine gaps were
worked.

- The Redis recovery path is now four steps, not three: `--apply` (fails) → `--repair-redis` →
  `--apply` again → `--verify`. `clearState()` is reached only by a successful apply, so the old
  repair-then-verify sequence passed every assertion while leaving the snapshot on disk and the
  entry looking mid-run. The rerun is idempotent — rows are already at the target and the retired
  pivot is already gone — and it is the only thing that finishes the run.
- `--apply` prints that exact sequence on a Redis mismatch, and `--repair-redis` checks for an
  outstanding snapshot and names the right next step for the state it is actually in (rerun the
  apply, or just verify).
- New end-to-end regression test raising the mismatch *during* an apply and proving all four
  steps: snapshot retained on failure, repair succeeds with the snapshot untouched, rerun clears
  it, verify passes. The pre-existing repair test corrupts Redis *after* a clean apply and so
  never has a snapshot to clear — it does not prove resumability.
- The production write freeze is now mandatory and named: `php artisan down`.
  `CheckForMaintenanceMode` sits in the global middleware stack with an empty `$except`, so every
  HTTP route 503s, and no queued job, listener or scheduled command writes `photo_tags`. "Run at
  the quietest hour" is gone — quiet traffic does not close the window.
- Documented why the `retired_at` guards are not a substitute: they refuse writes that *name* a
  retired object, but a tag replace or quick-tag sync that *omits* it never names it, and the
  guard reads without a row lock. A shared lock on the object row would close one of the three
  cases; the freeze closes all three. The pivot write lock stays as defence in depth, with the
  residual (a wedge, not data loss) described accurately.
- The 2026-08-09 rehearsal evidence in `TagRetirements-2026-08.csv` is marked VOID in place —
  history retained, not deleted — because the apply control flow changed after it was recorded.
  A fresh production-snapshot rehearsal is required before `PRODUCTION_APPLIED`.
- Removed the unrelated GOODNIGHT/GOODMORNING session-workflow block from `CLAUDE.md`; that file
  is now identical to the merge-base.

## Session — freeze procedure hardening, stale metadata, version decision (v5.13.2)

Fourth review round. No application-code findings; three readiness items.

- The write-freeze procedure is now an eight-step gate rather than one command. `php artisan down`
  gates request *entry*, not exit, and `config/app.php` has no `maintenance` key — so the driver
  is the framework default `file` and the flag is `storage_path('framework/down')` on local disk,
  making maintenance state **per-node**. The gate: enumerate every serving node; `down` on each
  (preferred over introducing the shared `cache` driver on the day, which would itself need
  committing, deploying and verifying identically everywhere); confirm `503` on the exact endpoint
  `GET /api/v3/user/photos` — `routes/api.php:82`, the same `auth:sanctum` v3 group as `POST` and
  `PUT /tags`, so a 503 there is direct evidence the write routes are down, and a `401` means the
  freeze is not on; verify nodes individually where the infrastructure allows, since one
  load-balanced request proves only that one backend answered; drain in-flight PHP/web requests
  via production's established procedure and wait out the maximum request lifetime; check
  `information_schema.innodb_trx` for open transactions; then the SQL snapshots; then the dry run.
  `--secret` is explicitly refused — every step is CLI, and the bypass cookie would turn the 503
  confirmation into a false negative.
- The drain guarantee is steps 5–6, **not** the SQL snapshots. Two identical `COUNT(*)`/`MAX(id)`/
  `MAX(updated_at)` readings prove nothing on their own: a request can hold an open transaction
  across both and commit afterward. They are recorded as a one-way backstop — if either reading
  moves, something is definitely still writing, and the run aborts.
- The production drain command is marked **[OPERATOR PREREQUISITE]**: it is external to this
  repository, must be established and recorded before the run day, and is deliberately not
  guessed at here.
- §E preamble no longer says entry 1 "is rehearsed" — it states the 2026-08-09 rehearsal is void
  and that a fresh one from a current production snapshot, on the exact commit to be deployed, is
  required before `PRODUCTION_APPLIED`.
- Queue `notes` corrected: the null-user metrics defect is recorded as RESOLVED 2026-08-13 with
  its test reference; the remaining blocker is named as the fresh rehearsal.
- **Version accepted at 5.13.2** (HEAD is 5.13.1). The 2026-08-13 session added `--repair-redis`
  and the survivor/ranking fixes — a patch bump under this project's rules, already labelled
  v5.13.2 in that day's changelog. Today's work is docs, tests and metadata only, so no further
  bump.
